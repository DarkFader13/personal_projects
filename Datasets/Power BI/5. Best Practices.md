## Preparing Data

### Dataflows Best Practices

#### Breaking Dataflows into Multiple Layers

- **Separate Staging and Transformation Dataflows**:
    - **Staging dataflows** focus on extracting and preparing raw data (e.g., data type changes, basic filtering).
    - **Transformation dataflows** handle the processing of data into its final format for analysis.
    - This separation simplifies development and reduces complexity by modularizing the dataflow process.
- **Multilayered Architecture**:
    - Store raw data in Dataverse or Azure Data Lake before transforming it in separate dataflows, improving performance and maintainability.

#### Use Custom Functions

- **Custom Functions for Reusability**:
    - If similar transformations are required across multiple queries, create a **custom function**.
    - Custom functions can be reused across tables, reducing redundancy and making maintenance easier.
    - Avoid duplicating transformation logic, keeping your dataflows clean and manageable.

#### Organize Queries Using Folders

**Group Related Queries**:Use **folders** in Power Query to organize queries by type or purpose. This enhances navigation and simplifies future maintenance, especially in larger dataflows.

#### Leverage Computed Tables

**Computed Tables for Better Performance**:
- Use **computed tables** to store intermediate results and reference them in other tables.
- Computed tables reduce redundant data transformations, making them faster and more efficient.

#### Utilize the Enhanced Compute Engine

**Optimize Joins and Filters**:
- Use the **enhanced compute engine** to perform joins and filter transformations in a computed table before applying more complex transformations. This optimizes performance in large dataflows.

#### Break Down Complex Steps into Multiple Queries

**Decompose Large Queries**:
- Instead of having one large query with many steps, break it down into smaller queries.
- Use **Enable Load** for intermediate queries, loading only the final table. This simplifies tracking and debugging of the transformation steps.

#### Document Queries and Steps

**Add Descriptive Properties**:
- Add **documentation** to queries and steps, including descriptions. These tooltips help you and others understand the logic behind each query and step, making future maintenance easier.

#### Ensure Capacity Is in the Same Region

**Region Consistency**:
- Ensure that **Premium capacity** is in the same region as your Power BI tenant to avoid issues with dataflows not being refreshed properly.

#### Separate On-Premises and Cloud Sources

 **Organize by Source Type**:
- Separate dataflows based on data source types (e.g., on-premises, cloud, SQL Server, Dynamics 365) for easier troubleshooting and improved refresh management.

#### Schedule Refresh Based on Dataflow Requirements

 **Separate Refresh Schedules**:
- Different data sources have different refresh requirements (e.g., hourly for sales transactions, weekly for product-mapping).
- **Break dataflows into separate workflows** and set refresh schedules according to the update frequency of each dataset.

#### Avoid Refresh Conflicts with Linked Tables

**Manage Refresh Schedules**:
- Avoid scheduling refresh for **linked dataflows** in the same workspace. Refreshing linked tables simultaneously can cause locking issues.
- To mitigate this, either **do not set refresh schedules for linked dataflows** or **move them to a separate workspace**.


### Power Query Best Practices
#### Choosing the Right Connector

- **SQL Server Connector:** Use the native **SQL Server** connector instead of **ODBC** for better performance and query folding.
- **ODBC/OLEDB:** If your data source isn’t listed, use these connectors to link to custom sources.
- **Connector Standardization:** Power Query follows a standardized experience across connectors, with features like **Data Preview** to help you preview and select relevant data easily.

#### Filtering Early

- **Filter Data Early:** Apply filters at the beginning of your query process. Some connectors, such as SQL Server, take advantage of **query folding** to optimize filtering, improving performance.
- **Type-Specific Filters:** Use type-specific filters for columns like **date, datetime**, and **time zone** to streamline data retrieval.

#### Efficient Query Operations

- **Expensive Operations Last:** Perform data operations that require full data scans (like sorting) later in your query to avoid delays.
- **Streamlined Operations First:** Filters and other lightweight operations should come early to reduce query load times.
- **Subset Data for Faster Previews:** When debugging slow queries, use a **Keep First Rows** operation to limit the data set size temporarily.

#### Using Correct Data Types

- **Data Types Matter:** Ensure correct data types are assigned to columns (e.g., dates, text). Missing data types can limit available features like type-specific filters and transformations.
- **Automatic Detection:** Power Query automatically detects data types for unstructured sources like **CSV** and **TXT** files.

#### Exploring Your Data

- **Data Profiling Tools:** Enable data profiling tools to understand your data better. These tools provide insights like:
    - **Column Quality** (valid, error, empty values).
    - **Column Distribution** (value frequency).
    - **Column Profile** (detailed statistics).
- **Data Preview:** Use these tools to analyze data before making any transformations.

#### Organizing Your Work

- **Documenting Steps:** Rename steps and add descriptions to help you and others understand transformations in the **Applied Steps** pane.
- **Modular Approach:** Split large queries into smaller, manageable pieces using **Extract Previous** to simplify and improve understanding.
- **Use Groups:** Group related queries in the **Queries pane** for better organization.

#### Future-Proofing Queries

- **Resilience to Changes:** Design queries to handle data source changes, such as dynamic rows or columns, without breaking.
- **Remove Bottom Rows** for dynamic rows with fixed footers.
- **Choose Columns/Remove Columns** for a fixed selection/removal columns, even with changing data.
- **Unpivot Selected Columns** to handle varying column structures.
####  Using Query Parameters

Query parameters in Power BI provide a dynamic way to filter and control data, making reports more flexible and efficient. They are particularly useful for managing different data environments (e.g., test vs. production) or filtering large datasets.

- **Parameter Creation:** Use the **Manage Parameters** option in Power Query Editor to define query parameters.
- **Filter Query:** After creating the parameter, apply it to the data query (e.g., filter stock orders by country).
- **Dynamic Filtering:** Set the filter to use the parameter's value rather than a static filter.
- **Reuse Parameters:** Use parameters in multiple steps, and manage them through the **Manage Parameters** window.
- **Custom Function Arguments:** Parameters can also serve as arguments in custom functions, simplifying repeated transformations.
- **Data Load:** After applying the filter, load the data to confirm the correct filtering based on the parameter value..

#### Creating Reusable Functions

- **Custom Functions:** If you frequently apply the same transformations, create a **Power Query custom function** to centralize your logic and reduce redundancy.
- **Invoke Custom Functions:** Once created, you can invoke your custom functions across multiple queries or datasets, saving time and improving consistency.   

### Computed tables Best Practices
> A **computed table** in Power BI is a table that’s created by referencing an existing table (either within the same dataflow or another dataflow). Unlike regular tables, which get data directly from the original data source, computed tables pull data from a previously ingested and stored table, applying additional transformations without reloading the data from the source.

#### Why Use Computed Tables?

Computed tables offer several advantages:

- **Improved Performance**: Transformations are applied only once, which reduces redundant processing and speeds up performance.
- **Reduced Load on Data Sources**: By reusing data stored in the data lake, the demand on the original data source is decreased.
- **Reusability**: Data and transformations can be shared across multiple tables, saving time and resources.

#### Creating a Computed Table

1. **Reference an Existing Table**:    
    - Right-click the **Orders** table in Power Query → select **Reference**.
    - This creates a new computed table (e.g., **Orders Aggregated**), which can then have further transformations (like **Group By**) applied.
2. **Apply Transformations**:    
    - Perform any necessary transformations (e.g., aggregation by customer) on the computed table.
    - The transformations in the computed table are faster since they are working with the data already loaded in storage.

#### Computed Tables in Other Dataflows

Computed tables can also be created from tables in **other dataflows** using the **Power Platform dataflow connector**. This allows you to reduce the read time from the data source and share common transformations across different dataflows.

#### Deciding When to Use Computed Tables
- **For Non-SQL Data Sources** (like CSV):
    - When **query folding** is not supported, it’s best to load the raw data into a source table without transformations. Computed tables can then perform the necessary transformations on the ingested data.
    - This reduces load on the data source and helps reuse the data in other reports or dataflows.
- **For SQL or Query Folding Sources**:
    - For data sources that support query folding (like SQL Server), apply common transformations in the source table. The transformations will be handled by the source, improving performance.
    - Use computed tables for transformations that only apply downstream, keeping them separate from the source table’s processing.

#### Benefits of Computed Tables

- **Performance Optimization**: By limiting redundant data loading and applying transformations only once, computed tables help reduce processing time.
- **Efficient Data Sharing**: Computed tables reduce the load on data sources, especially when used with large datasets or when accessed through gateways.

### Power BI Workspace Best Practices
#### Separate Staging/Extraction Dataflows from Transformation Dataflows

- **Staging Dataflows**: These dataflows focus only on extracting raw data from the source systems without any transformations. This allows the data to be reused across multiple other dataflows, reducing redundancy.
- **Transformation Dataflows**: Once the data is extracted in staging dataflows, it can be transformed in separate dataflows. This modular approach allows for easier maintenance and reusability of the data across different processes.

#### Use Multiple Workspaces
**Organizing Dataflows**: Divide dataflows into different workspaces based on their purpose, such as:
- **Company-wide dataflows**: For organization-wide tables or transformations.
- **Department-specific dataflows**: For dataflows specific to certain departments or teams.

#### Set Correct Access Levels on Workspaces

- **Access Control**: Ensure that users have the correct level of access to workspaces. 
#### Dataflow Endorsement Levels

 **Endorsement**: Dataflow authors can mark their dataflows with three levels of endorsement:    
- **No Endorsement**
- **Promoted**
- **Certified**

#### Split Tables Across Multiple Dataflows

- **Separate Tables by Refresh Requirements**:
    - If different tables require different refresh schedules, split them into multiple dataflows. For example, a sales table may need to be refreshed every 4 hours, while a product mapping table might only need weekly updates.
- **Benefits**:
    - **Custom Refresh Schedules**: Tailor refresh schedules for each table independently to optimize performance and reduce unnecessary data load.
    - **Improved Flexibility**: Allows for more granular control over the refresh process.

#### Reuse Dataflow Tables

- Tables that need to be used across multiple Power BI files or services are good candidates for dataflows. For example, a **Date** table that is used in multiple reports should be moved to a dataflow for easier reuse. 
- **Reduced Duplication**: Prevents duplicating tables across multiple reports, saving time and effort.
- **Centralized Data Management**: Makes managing data more efficient and consistent across different Power BI files or environments.

### Dimensional Modelling Best Practices
#### Layered Architecture

- **Multi-Layered Dataflows**: Separate staging and transformation dataflows into different layers to reduce maintenance complexity and improve scalability.
- **Benefits**:
    - **Minimizes Source System Load**: Reduces the number of reads, thus reducing load on source systems, especially on-premises systems.
    - **Data Reusability**: Staging dataflows can be reused across multiple dataflows, making transformations more efficient and consistent.
    - **Reconciliation**: Provides an intermediate copy of the data to verify and reconcile in case of changes in the source system.
    - **Separation from Source Systems**: Ensures transformation logic remains independent of the source system, which is useful when migrating to new systems.
    - **Performance Optimization**: Minimizes waiting time for data retrieval from slow connections since the staging dataflows already provide the data.
    - **Simplified Maintenance**: Changes made in one layer (e.g., data extraction) do not impact other layers, reducing complexity and improving troubleshooting.

#### Use of Computed Tables

- **Purpose**: A computed table sources data from an already-processed table (usually from a staging dataflow) to perform additional transformations.
- **Benefits**:
    - **Improved Performance**: Reduces redundant transformations and optimizes data processing speed.
    - **Reusability**: By reusing processed data, computed tables ensure consistency across dataflows and avoid duplicating transformation logic.

#### Building a Star Schema

- **Purpose**: Design your model using a **star schema**, consisting of **fact tables** and **dimension tables**, which allows for easier querying and reporting.
    - **Fact Tables**: Store numerical data, such as sales or transactions.
    - **Dimension Tables**: Store descriptive attributes like product names, regions, or time periods.
- **Benefits**:
    - **Optimized Queries**: Star schema improves query performance by minimizing the complexity of joins between fact and dimension tables.
    - **Simplified Reporting**: A well-structured model enables efficient analysis and clearer reporting.

#### Unique Key for Dimensions

- **Purpose**: Ensure each dimension table has a **unique key** to avoid weak relationships (many-to-many relationships).
- **Implementation**: Create unique keys by transforming columns or combinations of columns that return unique rows in the dimension.
- **Benefits**:
    - **Consistent Relationships**: Helps establish strong relationships between fact and dimension tables.
    - **Improved Integrity**: Ensures clean, accurate relationships in the data model.

#### Incremental Refresh for Large Fact Tables

- **Purpose**: For large fact tables, apply **incremental refresh** to reduce the amount of data being refreshed, focusing only on the data that has changed.
- **Benefits**:
    - **Improved Performance**: Refreshing only the changed data reduces resource consumption and improves refresh times.
    - **Optimized Storage**: Reduces the load on storage and reduces the volume of data transferred.

#### Referencing for Dimensions and Fact Tables

- **Purpose**: Reference common transformation logic to create both dimension and fact tables.
- **Benefits**:
    - **Centralized Transformation Logic**: Common data cleaning and transformation steps are done once, ensuring consistency.
    - **Efficiency**: By using references, data cleaning and transformation are optimized and reduce the processing time for both dimensions and facts.### Staging Dataflows

## Modelling Data 

### Model Design Best Practices 
- **Use a Star Schema** where possible for better performance and simpler queries.
- **Ensure relationships are correct** (one-to-many, proper filter direction).
- **Position dimension tables above fact tables** to reflect filtering logic.
- **Disable auto-detect relationships** for greater control over model design.

### Report Performance Best Practices 
#### USERELATIONSHIP (DAX)
- Avoid duplicating dimension tables; use `USERELATIONSHIP` for efficiency.
- Ensure relationships are correctly set before using the function.
- Consider the direction of filter propagation when applying `USERELATIONSHIP`.

#### Aggregation Measures
- Format measures correctly (e.g., currency for sales, percentage for profit margin).
- Use **existing measures within other measures** to improve readability and efficiency.

#### Reducing Cardinality
- Ensure fields participating in relationships have the same data type. For example, use integers or decimals instead of text for key columns.
- Reduce the precision of decimal numbers. Using **fixed decimal numbers** instead of general decimal types reduces storage and improves performance.
- In DAX calculations, explicitly define the data type and the number of decimal places to enhance efficiency.

#### Aggregation
- Pre-aggregate data for commonly used summaries, such as sales by year, month, or region, and import these summary tables into the data model.
- Aggregated tables can be created from detailed data tables, allowing Power BI to query summarized information rather than raw transactional data, speeding up report queries.
- Use Power BI's storage modes to optimize large datasets. For example, use **DirectQuery** for large fact tables and **Import** for smaller tables.

### SQL Best Practices 

#### Breaking SQL Queries into Multiple Data Sources

**Improved Performance**    
- Reduces the computational load on Power BI by breaking down complex queries into smaller, faster-executing parts.
- Results in quicker report generation and a more responsive user experience.
**Enhanced Maintainability**    
- Makes it easier to update, debug, and maintain the data model.
- Allows analysts to work independently on different parts of the project, especially in a team environment.
**Simplified Troubleshooting**    
- Easier to locate and fix issues in smaller, isolated queries than in a large, complex one.
- Reduces the time and effort required for troubleshooting performance problems.
**Optimized Data Loading**    
- Loads only the necessary data for specific reports, avoiding unnecessary data processing.
- Helps manage data more efficiently in terms of storage and processing.
**Customized Data Transformations**    
- Allows for specific transformations on each dataset, ensuring data is in the best format for analysis and reporting.
